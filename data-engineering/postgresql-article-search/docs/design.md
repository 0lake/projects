# Проектные решения

Исходная модель была учебным черновиком. При реализации в PostgreSQL в ней найдены места, где схема либо нарушает нормализацию, либо не даёт выполнить заявленные бизнес-процессы. Ниже перечислено, что изменено и почему.

## Что изменено в модели

| Было | Стало | Причина |
|---|---|---|
| `tag` содержит `user_id` и `article_id` | справочник `tag` и связь `article_tag` | тег «нейросети» должен существовать один раз и применяться ко многим статьям, иначе название дублируется в каждой строке |
| `user.subscription_id` указывает на подписку | `subscription.user_id UNIQUE` | цена и статус оплаты принадлежат человеку, а не общей строке; иначе одна просрочка деактивировала бы всех, кто ссылается на ту же подписку |
| `search` связывает пользователя и статью | `favorite` (избранное) и `search_query` (история запросов) | в бизнес-процессах это два разных факта: «добавил в избранное» и «искал такой-то текст» |
| у `review` нет оценки | `review.rating` от 1 до 5 | бизнес-процесс «оценить статью, влияя на общий рейтинг» невыполним без числа |
| общий `status_enum` для пользователя, статьи и подписки | пять отдельных типов | у каждой сущности свой жизненный цикл, общий тип допускает бессмысленные значения вроде статьи «онлайн» |
| `nation_enum` | `CHAR(2)` по ISO 3166-1 | список стран в ENUM пришлось бы менять миграцией, а код страны проверяется регулярным выражением |
| регулярка email с четырьмя доменами и без точки в имени | общий формат адреса | `anna.k@mail.ru` отвергался исходной маской, а `x@corp.org` тоже был бы недопустим без причины |
| телефон: сложная маска с пробелами и скобками | формат E.164 `+79990000001` | один канонический формат, по нему легко искать и сравнивать |
| возраст проверялся триггером | `CHECK (age BETWEEN 18 AND 120)` | правило над одной строкой, которое не зависит от других данных, лучше выражать ограничением: оно работает и для `COPY`, и для массовых обновлений |
| `size` хранился вручную | `GENERATED ALWAYS AS (char_length(content))` | значение нельзя ввести неверно |
| `table user` | `app_user` | `user` зарезервированное слово, ради него пришлось бы везде писать кавычки |

## Триггеры

| Триггер | Что делает |
|---|---|
| `article_author_stats` | при добавлении, смене и удалении авторства пересчитывает `total_articles` и рейтинг автора |
| `review_updates_rating` | при любом изменении отзыва пересчитывает рейтинг статьи как среднее |
| `article_rating_to_authors` | при изменении рейтинга статьи пересчитывает авторов (цепочка отзыв, статья, автор) |
| `review_published_only` | запрещает отзыв на черновик и архивную статью |
| `subscription_user_status` | просрочка больше месяца деактивирует пользователя, возврат к «активна» возвращает доступ |
| `subscription_touch` | обновляет `updated_at` |

Исходный триггер увеличивал счётчик статей автора на единицу при вставке. Это ломается при удалении связи, повторной загрузке данных и ручных правках. Здесь значения всегда пересчитываются по источнику (`COUNT`, `AVG`), поэтому расхождение невозможно.

Исходная функция «средний рейтинг статьи» считала `AVG(rating)` по самой таблице `article` для одного `article_id`, то есть возвращала рейтинг статьи без усреднения. Теперь рейтинг усредняется по отзывам.

## Полнотекстовый поиск

Требование «поиск по ключевым словам» реализовано средствами PostgreSQL, а не `LIKE`:

- столбец `search_vector` (`tsvector`) генерируется из заголовка с весом `A` и текста с весом `B`;
- GIN-индекс по нему;
- функция `search_articles(query, category, limit)` использует `websearch_to_tsquery('russian', ...)`: поддерживает фразы в кавычках, `OR` и исключение слова через минус;
- результат упорядочивается по `ts_rank_cd`, затем по рейтингу и просмотрам;
- в выдачу попадают только опубликованные статьи.

Поиск использует стемминг русского словаря: «цены» находит «цен». Он не знает синонимов, поэтому «инфляция» не найдёт «рост цен». Для синонимов нужен словарь тезауруса или векторный поиск, это за рамками проекта.

Бенчмарк на 100 000 статей ([`benchmark/results.txt`](../benchmark/results.txt)): запрос по редкому слову выполняется за 1,6 мс с GIN-индексом и за 37 мс последовательным сканом, примерно в 23 раза быстрее.

## Ограничения, о которых стоит знать

- `author.total_articles` считает все связанные статьи, включая черновики и архив, а `top_authors` только опубликованные. Это сделано намеренно: первое отражает объём работы автора, второе публичный рейтинг.
- Материализованное представление `top_authors` не обновляется само: `REFRESH MATERIALIZED VIEW CONCURRENTLY top_authors` нужно запускать по расписанию или после пакетной загрузки.
- Хеши паролей в тестовых данных условные (`md5`). В реальной системе нужен bcrypt или argon2 на стороне приложения.
