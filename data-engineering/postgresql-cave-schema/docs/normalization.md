# Нормализация и денормализация

Анализ выполнен для схемы из [`sql/01_schema.sql`](../sql/01_schema.sql). Обозначения: `A -> B` означает, что значение `A` однозначно определяет значение `B`.

## Функциональные зависимости (минимальное покрытие)

| Отношение | Зависимости |
|---|---|
| `location` | `location_id -> name, coordinates`; `name -> location_id` (UNIQUE) |
| `cave` | `cave_id -> size, age, depth` |
| `gallery` | `gallery_id -> size, carving_technique, cave_id`; `cave_id -> gallery_id` (связь 1:1) |
| `penguin` | `penguin_id -> habitat, population_size, behaviour, current_location, status` |
| `human` | `human_id -> name, age, gender, emotion, current_location, status` |
| `creature` | `creature_id -> name, speed, description, current_location, status` |
| `fog` | `fog_id -> visibility, density, duration_time` |
| `explore`, `chase`, `blur` | неключевых атрибутов нет, ключ составной и включает все столбцы |

Все зависимости нетривиальные, левые части неприводимые.

## Нормальные формы

**1NF.** Все атрибуты атомарны, у каждого отношения есть первичный ключ. Составных и многозначных значений нет.

**2NF.** У отношений с простым ключом частичных зависимостей быть не может. В ассоциациях `explore`, `chase`, `blur` нет неключевых атрибутов, поэтому зависеть от части ключа нечему.

**3NF.** Транзитивных зависимостей нет: неключевые атрибуты зависят только от первичного ключа и не определяют друг друга. Отдельно проверены кандидаты на транзитивность:

- `current_location -> ?` ничего не определяет, координаты места лежат в `location`, а не в участниках;
- `status` вычисляется по составу участников в месте, а не по другим столбцам своей строки. Это производный атрибут, и его поддерживает триггер (см. ниже).

**BCNF.** Каждый детерминант является потенциальным ключом. У `location` и `gallery` два потенциальных ключа (`location_id` и `name`, `gallery_id` и `cave_id`), но они простые и не пересекаются, поэтому аномалий, характерных для 3NF без BCNF, нет.

Вывод: схема уже находится в BCNF, декомпозиция не требуется.

## Что изменилось по сравнению с исходной моделью

- Столбец `current_location` добавлен в `creature`: в исходной даталогической модели его не было, хотя зависимости и триггер на него опирались.
- В `penguin`, `human`, `creature` добавлен `status`: без него триггер не мог бы ничего записать.
- Для `fog` взят набор столбцов из DDL (`visibility`, `density`, `duration_time`), так как перечисление атрибутов в описании сущностей скопировано с другой сущности (имя, национальность и т.д. относятся к человеку).
- `Pinguin` и `Chaze` исправлены на `penguin` и `chase`.

## Денормализация

Пещера и галерея связаны 1:1 и почти всегда читаются вместе. Физическое слияние таблиц сломает 3NF: появится зависимость `cave_id -> gallery_size`, часть столбцов станет `NULL` для пещер без галереи, а целостность придётся защищать вручную.

Поэтому вместо слияния используется материализованное представление `cave_gallery_mv` ([`sql/04_denormalization.sql`](../sql/04_denormalization.sql)):

| | Слияние таблиц | Материализованное представление |
|---|---|---|
| Чтение без JOIN | да | да |
| Нормализованное хранение | нет | да |
| Стоимость записи | аномалии обновления | `REFRESH` по расписанию или после изменений |
| Риск рассинхронизации | есть | управляемый, данные пересобираются из источника |

Стоит применять, если выборка «пещера плюс галерея» доминирует над записью. При редком чтении достаточно обычного JOIN по уникальному индексу `gallery.cave_id`.
