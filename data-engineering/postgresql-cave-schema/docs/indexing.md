# Индексы и планы запросов

Задача: для двух запросов предложить индексы, описать возможные планы без индексов, выбрать оптимальный и сравнить с фактическим `EXPLAIN ANALYZE`.

Исходная учебная база недоступна, поэтому таблицы `people`, `sessions`, `records` воссозданы по структуре запросов, а данные сгенерированы ([`indexing/00_synthetic_schema.sql`](../indexing/00_synthetic_schema.sql)): 20 000 человек, 150 000 сессий, 200 000 записей ведомостей, `setseed` фиксирует генерацию. Абсолютные значения времени зависят от машины, смысл имеет сравнение планов до и после.

## Запросы

1. Фамилия человека и учебный год его сессий за конкретную дату (`people LEFT JOIN sessions`).
2. Имя, идентификатор записи ведомости и дата сессии для человека с заданной фамилией и записью (`people LEFT JOIN records LEFT JOIN sessions`).

Замечание о `LEFT JOIN`: условия по правой таблице в `WHERE` отбрасывают строки без пары, поэтому оба запроса по смыслу являются `INNER JOIN`. Планировщик это видит и выбирает порядок соединения свободно. Если нужна настоящая левая выборка, условие по правой таблице переносится в `ON`.

## Возможные планы без индексов

| План | Шаги | Оценка |
|---|---|---|
| A | Полный скан обеих таблиц с фильтрами, затем Hash Join или Nested Loop | Фильтры применяются до соединения, на соединение идёт мало строк |
| B | Соединить таблицы целиком, затем отфильтровать результат | Соединяются все строки, фильтр поздно |

Оптимален план A: фильтр до соединения уменьшает вход соединения на порядки. Именно его строит PostgreSQL.

## Фактический результат

| | Без индексов | С индексами |
|---|---|---|
| Запрос 1 | Seq Scan по `sessions`, Nested Loop, 10,5 мс | Bitmap Index Scan по обеим таблицам, Hash Join, 1,1 мс |
| Запрос 2 | Seq Scan по `sessions`, 10,8 мс | Index Scan по первичному ключу и `idx_sessions_person`, 0,045 мс |

Полные планы: [`before_indexes.txt`](../indexing/plans/before_indexes.txt), [`after_indexes.txt`](../indexing/plans/after_indexes.txt).

## Предложенные индексы

| Индекс | Зачем |
|---|---|
| `people (last_name)` | фильтр по равенству фамилии |
| `sessions (session_on, person_id)` | фильтр по дате, `person_id` в индексе сокращает обращения к таблице |
| `sessions (person_id)` | внешний ключ для соединения с `people` |
| `records (person_id)` | внешний ключ для соединения с `people` |

Первичные ключи проиндексированы автоматически.

## Почему B-tree, а не hash

В учебной работе предлагались hash-индексы под фильтры по равенству. Hash действительно работает только для `=`, и в PostgreSQL 10+ он надёжен, но B-tree выбран осознанно: он покрывает и равенство, и диапазоны по дате, поддерживает составные ключи и сортировку, а выигрыш hash на таких объёмах незаметен. Составной индекс `(session_on, person_id)` с hash невозможен.
